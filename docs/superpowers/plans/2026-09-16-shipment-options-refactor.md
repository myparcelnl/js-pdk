# INT-1844 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the capabilities API decide what a shipment option can be, so that one thing answers the question and a person reading any of the three codebases can say where a value came from.

**Architecture:** Three rules. Every layer below follows from one of them.

- **The API answers what is possible.** Capabilities takes the options currently switched on and returns the resolved state, including `requires`, `excludes` and the cases where they contradict each other. No codebase walks those rules itself.
- **A stored value means somebody chose it.** The response still binds: a required option is on and locked, an excluded one is off and gone, and that is what exports. It is worked out fresh from the response each time rather than written back into the order as though a merchant had set it. So when the option that caused it is switched off, what the merchant actually chose comes back, instead of a value nobody picked being left behind.
- **One set of names inside.** Capability keys (`requiresSignature`) in the code. Legacy names (`signature`) only where the v1 API demands them.

**Tech Stack:** PHP 7.4 (floor), Pest 1.x, Guzzle, generated MyParcel SDK. TypeScript, Vue 3, Pinia, TanStack Query, Vitest.

**Spec:** `docs/superpowers/specs/2026-09-16-shipment-option-determination.md`

**Ticket:** INT-1844.

All line ranges below are on `origin/main`, re-measured 2026-09-16. An earlier draft measured them
against the three closed PR branches; that is corrected.

What it gave us and this plan keeps: fields generated by looping over `carrier.options` rather than

Two of the three defects listed against it below — the one-hop depth and the missing record of which
option locked a target — follow from that design's choice to apply dependencies in `afterUpdate`,
not from neglect. It shipped reviewed.

Three of its decisions never landed or drifted, and are noted where they matter below:
`fieldDependencies.ts` was never created because the API supplied the data instead,
`priorityDelivery` was dropped entirely, and refs are built from the union of every carrier's option
keys rather than the selected carrier's.

## What decides a value, and in what order

These are preconditions, not description. No layer in any stack may violate one. If a change
appears to need an exception, the change is wrong, not the rule.

Each step narrows. None widens. That holds because one thing owns the decision, not because
something enforces it separately.

1. **The account's contract definitions** decide which carriers exist, which options each one
   holds, each option's carrier default, and whether it is always required. Subscription and
   account concerns are part of this, not separate. The settings screens are built from it.
2. **Merchant settings**, per carrier: an export default as a tri-state, and an `allow` flag.
3. **Product settings**, per product, tri-state. An option switched on by any product wins over one
   switched off, whatever order the products sit in.
4. **Capabilities for the resolved shipment** decides what is possible, required and excluded. It
   is not asked in ignorance of the steps above it: the request carries carrier, destination,
   package type, delivery type, weight **and the options steps 1 to 3 resolved to on**. It answers
   about that shipment, not about a blank one. In the checkout the delivery_options endpoint
   narrows further, per delivery moment.
5. **The consumer's pick**, limited to what step 2 allows and step 4 permits.
6. **The merchant's edit in the admin** — step 4 again, second entry point, same mechanism.
7. **Export does not decide anything.** It sends, and the API rejects what it will not accept.

In code, steps 1 to 3 are the helper chain in `PdkOrderOptionsService::calculateShipmentOptions()`
resolved by `TriStateService::resolve` — first answer that is not inherit wins — and step 4 is one
capabilities request carrying what that chain switched on.

### The rules that go with it

- **`allow` governs whether the consumer gets a control. It never governs the value.** An option
  the carrier requires and the merchant disallowed is on, and the consumer simply has no checkbox
  for it.
- **A stored value means somebody chose it.** Required, excluded and unavailable are worked out
  from the response each time and never written back as though a merchant had set them.
- **The order stores tri-states, including inherit**, and resolution runs on read. It holds what the
  next export should use, not what a past export produced.
- **Package type and delivery type resolve before options**, because the capabilities request needs
  them.
- **When capabilities cannot be reached, every surface fails loudly and changes nothing.**
- **An option is consumer-facing when it has an allow setting.**
- **Do not funnel the merchant.** In the admin, a merchant must never have to work out by
  elimination which earlier choice is blocking them. An option that has become impossible stays on
  screen, locked, with the reason next to it. It does not disappear. The control the merchant used
  is always still clickable, and undoing it restores exactly what was there before. The consumer
  side may hide an impossible option, because a consumer is choosing, not administering.

  This is the one place the API's answer is not rendered as-is. Capabilities resolves an exclusion
  by **removing** the option from the response — `requiresReceiptCode` simply vanishes once age
  check is requested. Rendered literally, a merchant who wants receipt code sees no receipt code at
  all and no hint that age check is why. The admin therefore needs both answers: the baseline
  response with no options sent, which says what this carrier and destination could offer, and the
  current response, which says what the present selection allows. What is in the first and missing
  from the second is shown locked, not dropped.

### Gate

Before a layer is reviewed, answer these against it:

- Does anything in this layer let a later step widen what an earlier one narrowed?
- Does anything write a computed value into stored data?
- Does `allow` affect a value anywhere in it?
- Does a failed or missing capabilities response change a stored choice?
- Can a merchant reach a state they cannot get out of by undoing what they just did?
- Does an option ever leave the admin screen without saying why?

A yes to any of those is a blocker, not a discussion.

## How we judge this

Line count is the last measure, not the first. The bar is whether a person can grasp it.

| Measure | On `main` | After this ticket |
| --- | --- | --- |
| Implementations of the requires/excludes rule | 3, and they disagree | 0 |
| Of those, covered by a test that pins conflict behaviour | 1 | n/a |
| Places that answer "is this option available, allowed or on" | 16 call sites in PHP, 1 admin, 1 widget | 1 |
| Separate pieces of state that must agree, admin | 11 | 3 — the baseline response, the current response, and what the merchant chose |
| Owners of `props.readOnly` on an option field, admin | 2, last writer wins | 1 |
| Deepest requires chain the admin can resolve | 1 | whatever the carrier defines |

The first two rows are the point. On `main` the three implementations resolve a contradiction three different ways: pdk by `orderOptionDefinitions` array order, the admin not at all because its traversal stops after one hop, and the widget by letting `forcedOn` win. Only the widget's rule is tested.

What replaces them is a set difference between two responses. That is the real simplification, and it is about the kind of problem rather than the size: no recursion, no cycle guard, no visited set, no tie-break, no dependence on array order or JSON key order. A reviewer can hold "what was possible, minus what is possible now" in their head.

**What this costs, stated plainly.** Keeping the merchant out of a funnel means one extra request per surface and a diff step that does not exist today — "render what the API returns" would have been simpler, and we are not doing that. It also adds a failure mode: the two responses must describe the same shipment, or the diff reports locks that are not real. That is the same race `readShipmentSnapshot` already guards on `main` by comparing against the debounced selection rather than the live form value, so the pattern exists, but it is new surface and it needs the same guard.

The second request cannot be avoided. Contract definitions know which options a carrier holds but not what this destination and weight allow, so an option present there and absent from the response could be blocked by the shipment or by the selection — and those two need different UI.

Line count is reported as evidence, not as the target: **102 lines** of traversal in pdk, **88** in the admin, and the widget's whole **120-line** `useShipmentOptionRules.ts`, plus roughly **550** lines of tests that exist only to pin rules the API already applies.

The other measures I quoted earlier — twelve pieces of admin state, two files needing a header diagram, five names per option — came from branch code and do not describe `main`. Collapsing the option definition classes was dropped from scope, so the name count does not move at all.

## What gates what

INT-1920 is deciding rate limiting on capabilities, and until it lands nothing may commit to more requests. That constraint is temporary, so this plan does not build anything to work around it — it waits.

The layer order below puts everything that adds no requests at the bottom of each stack, so the blocked line is a clean cut.

- **pdk layers 1 to 3** and **js-pdk layer 1** add no requests. Mergeable now.
- **pdk layer 4** widens the `md5(json_encode($args))` cache key in `CarrierCapabilitiesRepository`, raising the miss rate. **js-pdk layer 2** and **delivery-options layer 1** refetch when an option is toggled. All blocked.

The useful question for INT-1920 is not whether we may add calls but where. The admin is a small number of authenticated merchants clicking through a modal, behind a debounce and a client cache — a handful of extra requests per order edit. The checkout is consumer traffic, and it is the volume that makes rate limiting hard.

Also worth knowing before anyone sizes the increase: the proxy path is uncached. `CapabilitiesAction` calls `CapabilitiesService` directly, while the repository cache covers only the calculator path. Adding a cache there may take most of the admin increase off the table.

**Three decisions this layer must take deliberately:**

- The cache key now carries the selection, so entries multiply. Omit `options` entirely when nothing is on, so today's requests keep today's keys.
- `disableAllOptions()` `:73-88` fires when no capability matches at all. With options in the request an invalid combination becomes a normal answer, so it must fall back to a baseline request rather than disable everything. **This is the gate question about failed responses.** As written, an unreachable API silently switches every option off and exports that. It already violates "fail loudly and change nothing", and this layer must not carry that behaviour forward.
- **This is a behaviour change, not only a refactor.** Today the outcome of a contradiction depends on the order of `orderOptionDefinitions`, and an `isRequired` set in the first pass can be silently overwritten by an `excludes` in the second. Nothing logs it. Anything relying on that ordering shifts.

**The tests will not catch a regression here.** There is no cycle test, no contradiction test and no diamond test anywhere in the 498-line suite — I grepped `main` for `circular|cycle|visited` and the only hit is an unrelated fixture. The three traversal tests cover single-edge requires, single-edge excludes and a three-step chain, all happy paths. A green suite after this layer would not prove the API's answer matches the old one. Write the comparison cases first.

**Blocked on INT-1920.**

On `main` the rules live in one hook. `createShipmentOptionField.ts` is **107 lines**; `useCapabilitiesAutoClear.ts` is **452**.

**Deletions, exact:**

- its now-unused imports of `setFieldRef` and `FIELD_SHIPMENT_OPTIONS_PREFIX`, and the doc paragraph at `:13-16`
- `useCapabilitiesAutoClear.ts:427-447` — the option-availability scan, superseded by mirroring the resolved `options` set — plus `lineForOptionClear` `:307-311` and `optionLabelKey` `:38-42`, which have no other caller, and the `allOptionKeys` parameter `:134` with its uses at `:193` and `:434`
- `createShipmentOptionField.spec.ts:59-176` — the entire `afterUpdate dependency logic` block
- `useCapabilitiesAutoClear.spec.ts:269-308`

**Survives, and this corrects an earlier draft.** The invalid-combo machinery is orthogonal to option rules and stays: `readShipmentSnapshot` `:63-101`, `resolveInvalidCombo` `:319-348`, `revertAxis` `:241-254` and the axis watchers `:201-239` and `:350-408`. An empty `results` is still the signal that carrier, package type and delivery type do not go together.

`visibleWhen` `:35` and `disabledWhen` `:36-39` keep their meaning — "is the key present in the resolved options" — and become sufficient on their own, because an excluded option now comes back absent.

**Three defects this closes rather than preserves:**

- **The traversal is one hop deep.** `setFieldRef` mutates the ref directly and bypasses the update pipeline, so `afterUpdate` never re-enters. A requires B and B excludes C is never resolved today.
- **There is no record of which option locked a target.** On disable it re-derives the lock from `isRequired` alone (`:76-80`, `:96-100`), so if two enabled options both require signature, switching one off releases the lock for both.
- **Two writers own `props.readOnly`** — the imperative writes above and the declarative `readOnlyWhen` `:40-44`, last writer wins. Deleting the hook makes `readOnlyWhen` the only owner.

**Two responses, not one, and this is the detail most likely to be missed.** The baseline is the response to a request with no options sent — which is exactly the shipment-scoped query `main` already has, registered under `${orderId}.shipment` in `wireProxyCapabilities.ts`. The current is a second query carrying the selection. So the admin ends with three registered queries, not two, and the existing one keeps its job unchanged.

Both are needed, for two reasons.

The lock comes from the baseline: an option the carrier always requires. Required-because-of-a-choice is the difference between the two. `readOnlyWhen` reads `isRequired` directly today, so conflating them locks the toggle the merchant just clicked, and they are stuck. INT-1844's developer notes say the same.

Keeping the merchant out of a funnel needs the same pair. Capabilities resolves an exclusion by removing the option from the response, so an option present in the baseline and missing from the current is exactly "possible for this shipment, blocked by what you just chose" — which is what gets rendered locked with a reason, rather than dropped.

The cost is bounded: the baseline only refetches when carrier, destination, package type, delivery type or weight change. Option toggles refetch the current response only.

**Guard the pair.** The diff is only true while both responses describe the same shipment. Change the carrier and, for one render, the baseline still describes the old one and the difference reports locks that do not exist. `main` already solves this shape: `readShipmentSnapshot` compares against the debounced selection rather than the live form value precisely to avoid a false `invalid_combo` during the debounce window. Apply the same rule — a diff is only rendered when both responses were fetched for the same selection, and until then the previous state stands.

**Ships with layer 3, not before it.** A locked option with no reason fails the gate.

**Two things this layer must decide and currently does not.**

*Insurance.* `createInsuranceField` builds on `createShipmentOptionField`, so deleting the
`afterUpdate` hook changes what insurance inherits. Insurance is also not a toggle — it is an amount
with bounds read from the response — and the rendering model here is toggles, locks and reason
lines. Say what `fieldFactoryRegistry` holds after this layer and what an amount-typed option does
when it is required or blocked.

*`isSelectedByDefault`.* It is unimplemented on `main`: six hits in `apps/admin/src`, all in
`.spec.ts`, none in production code. The April design made it a decision with tests and it never
landed. This plan's step 4 names `isRequired`, excluded and unavailable, and says nothing about an
option the carrier switches on by default. It is a live hole with no owner — either implement it
here or file it, but do not leave it unnamed a third time.

**Cost, accepted:** every option toggle becomes a debounced refetch. The infrastructure already aborts stale in-flight requests and dedupes by serialised request.

### Layer 3 — say why

**Blocked**, depends on layer 2, and **required by it**. Separate layer because it is separately reviewable, not because it is optional. Layer 2 does not reach merchants without it.

One reason line on an option, shown only where capabilities or a rule overruled what the merchant set. The tri-state control already draws inheritance, so text everywhere else is noise.

This is what keeps the admin out of a funnel. An option that has become impossible stays on screen and locked; without the line, the merchant sees a dead control and has to find the cause by switching things off one at a time. Two cases carry a reason: the option is locked on because something else requires it, and the option is locked off because something else excludes it — the second being the one that would otherwise vanish from the response entirely.

This amends INT-1844's original "no explanatory text" criterion, which is struck through on the ticket.
